# Codex 目标模式提示词：完成 LyricRelay MVP

下面的内容可以直接复制到 Codex 的目标模式中。它要求 Codex 在当前仓库内完成可运行、可验证的 MVP，而不是只生成目录或设计文档。

```text
你正在负责完成 E:\LyricRelay 项目的 MVP。请遵守仓库根目录 AGENTS.md、系统指令和现有项目文档。本任务的最终目标不是“写出一些代码”，而是交付一个经过测试、可手工验收、没有伪实现的 Android → Windows 任务栏同步歌词闭环。

==================================================
一、产品目标
==================================================

LyricRelay 的唯一 MVP 价值是：

    手机听，电脑看。

用户继续使用 Android 手机上的原音乐播放器和蓝牙耳机。Android Companion 读取系统 MediaSession 的当前歌曲和播放进度，经同一局域网同步到 Windows Client。Windows Client 自动获取时间轴歌词，按手机播放进度计算当前歌词，并只在 Windows 任务栏显示歌词。

必须满足：

    Android 音乐播放器 → MediaSession → Android Companion
    → Android/Windows 设备链路 → Windows Client
    → 同步歌词 Provider → LRC/时间轴引擎 → Windows Taskbar

MVP 不传输手机音频，Windows 不播放声音，不要求用户更换播放器。

==================================================
二、绝对范围边界
==================================================

允许实现的范围：

1. Android Companion
   - 读取当前活跃 MediaSession。
   - 获取 title、artist、album、duration、packageName。
   - 获取 playing、paused、stopped、position、playbackSpeed。
   - 监听切歌、播放、暂停、Seek、播放器切换。
   - 通过局域网向 Windows 发送状态。
   - 支持一次配对的一台 Android 手机和一台 Windows 电脑。

2. Windows Client
   - 显示一次性 QR 配对信息。
   - 发现并自动连接已配对 Android 手机。
   - 接收和校验跨端协议消息。
   - 按歌曲 Metadata 获取时间轴歌词。
   - 解析 LRC 或等价的时间轴格式。
   - 根据 position、playbackSpeed、state 和本地单调时钟计算当前歌词。
   - 只在 Windows 任务栏显示单行或双行歌词。
   - 提供必要的开机启动、自动连接、显示开关和基础样式设置。

3. 必须具备的工程能力
   - Android 和 Windows 都有真实可构建的工程。
   - 核心协议、LRC 解析和 Timeline Engine 有自动化测试。
   - 设备断线、歌词请求失败、任务栏不可用时有明确降级行为。
   - 文档、协议示例、构建命令和验收记录与代码一致。

明确禁止加入：

- 手机音频传输、AudioPlaybackCapture、麦克风、ASR、Whisper。
- 播客字幕、视频字幕、实时翻译、AI 摘要或 AI 笔记。
- Windows 音频播放、手机投屏、自己做音乐播放器。
- 桌面悬浮歌词、全屏歌词、歌词窗口或浏览器页面歌词。
- 云同步、用户账号、登录、播放历史、歌单、推荐系统。
- 多台手机同时连接、iOS、macOS。
- 与 MVP 无直接关系的插件系统、复杂主题系统、代码生成器或云基础设施。

如果某个实现方案会扩大上述范围，停止扩展并选择更简单的方案。

==================================================
三、默认技术与兼容目标
==================================================

除非当前仓库已有更明确的技术决定，否则使用：

- Android：Kotlin + Android SDK，优先使用系统 MediaSession 能力。
- Windows：C# / .NET，使用 Win32 互操作隔离任务栏集成。
- 协议：版本化 JSON 消息；跨端字段以 packages/protocol 为唯一来源。
- 连接：同一局域网服务发现 + 长连接；可使用 WebSocket/TCP 等轻量实现，但必须有认证和加密设计。
- 歌词：Windows 侧 Provider Adapter；MVP 接入 QQ 音乐、网易云、酷狗和 LRCLIB 四个在线来源，暂不支持本地歌词文件。
- 测试：核心逻辑使用无平台依赖的自动化测试；平台 UI 使用布局测试和真实 Windows 手工验收。

若 Android minSdk、Windows target 或具体 Provider 未被仓库明确规定：

1. 先检查当前环境和现有文档。
2. 选择能覆盖主流设备且实现复杂度最低的合理版本。
3. 将选择写入设计文档和 README，不要把假设藏在代码里。
4. 不因为环境缺少 SDK、模拟器、实体手机或歌词服务就伪造测试通过。

==================================================
四、执行方式
==================================================

先检查：

- 根目录 AGENTS.md。
- README.md、docs/、specs/mvp/ 和 packages/protocol/。
- 当前工作区的已有修改、可用 SDK、编译器、测试工具和环境限制。

然后建立并持续维护一个短计划，按以下顺序执行：

阶段 0：基线和工程落地
- 确认技术版本、构建方式和支持矩阵。
- 把当前占位目录变成真实 Android 和 Windows 工程。
- 保留现有模块边界，不把所有逻辑塞到 App 入口。

阶段 1：协议与核心模型
- 实现 protocol v1 的 envelope、link.hello、pairing.confirm、track.state、track.cleared、link.ping 和 link.pong。
- 增加消息校验、版本校验、状态版本和旧消息拒绝。
- 两端使用各自模型映射，不复制出第二份互相矛盾的协议。

阶段 2：Timeline Engine 和 LRC Parser
- 先写测试，再实现纯逻辑核心。
- 时钟必须可注入；不得在核心逻辑中直接依赖墙上时间或 Thread.Sleep。
- 实现播放、暂停、恢复、Seek、速度变化、周期校准、边界裁剪和切歌失效。

阶段 3：设备配对与连接
- 实现一次性 QR 配对、已配对设备校验、局域网发现、长连接、心跳、超时和重连。
- 后续连接必须认证并加密；服务发现不能代替设备凭据。
- 连接恢复后 Android 必须发送完整 track.state。

阶段 4：Android MediaSession
- 实现用户可理解的授权和未授权状态。
- 选择当前正在 playing 的活跃 MediaSession；多个候选时采用确定性规则并写入文档。
- 无可用 MediaSession 时发送 track.cleared 或等价的明确空状态。
- 状态变化立即发送；播放中周期性发送校准点，不发送高频逐帧进度。

阶段 5：Lyrics Provider
- 实现 QQ 音乐、网易云、酷狗和 LRCLIB Provider，并按播放器包名路由、按失败继续兜底。
- Provider 只负责查询和格式转换，不把网络细节泄漏给 Timeline Engine。
- 处理超时、无结果、无时间轴歌词、非法格式、取消旧请求和切歌竞态。
- 不把未经授权的抓取、硬编码歌词或固定测试歌词作为生产实现。

阶段 6：Windows Taskbar Renderer
- 参考 TaskbarLyrics 的技术思路，但不复制其代码，不把它作为运行时依赖。
- 将 Shell_TrayWnd、UI Automation、DPI、任务栏方向和 DirectWrite/Direct2D 细节隔离在 Taskbar 适配层。
- 不创建桌面悬浮窗口，不遮挡系统托盘和应用图标，不抢焦点。
- Shell 不可识别时安全隐藏歌词，不影响连接、歌词获取和核心状态。

阶段 7：端到端验收
- 使用真实构建产物验证 Android → Windows 的完整链路。
- 至少验证首批重点播放器中的三种；优先网易云音乐、QQ 音乐、Spotify、YouTube Music。
- 记录自动化测试命令、手工测试环境、测试结果、已知限制和未覆盖项目。

每完成一个阶段都运行对应测试。遇到失败先定位并修复，不要为了让测试变绿而删除测试、放宽断言、屏蔽异常或写假实现。

==================================================
五、强制架构约束
==================================================

目录和依赖方向应保持：

apps/android-companion
  media → state → link → protocol mapping

apps/windows-client
  link → application state
  lyrics provider → parser → timeline → taskbar adapter

packages/protocol
  只承载跨端稳定契约和示例，不承载 Android、Windows UI、网络库或歌词 Provider。

硬性要求：

- Timeline Engine 不依赖 Android、Windows UI、网络或真实时间。
- LRC Parser 不依赖网络 Provider。
- Provider 通过接口隔离，并可以用固定响应测试。
- Taskbar Renderer 不参与歌词匹配和时间轴计算。
- Android 不决定 Windows 当前显示哪一行歌词。
- 新歌曲以 trackId 为边界；旧歌词请求返回后不得覆盖新歌。
- 所有异步请求都必须可取消，或在提交结果前校验 trackId。
- 位置统一使用整数毫秒；速度必须为正数且有合理范围校验。
- 日志不得记录配对密钥、完整 QR、歌词全文或不必要的个人数据。

==================================================
六、协议和同步规则
==================================================

消息 envelope 至少包含：

- version
- type
- messageId
- deviceId
- sentAt
- payload

track.state payload 至少包含：

- trackId
- title
- artist
- album
- durationMs
- packageName
- state：playing / paused / stopped
- positionMs
- playbackSpeed
- stateVersion

协议行为：

1. title 必填；其他歌曲 Metadata 缺失时不得导致整条状态丢失。
2. durationMs 未知时使用 null；positionMs 不得小于 0。
3. playbackSpeed 缺失按 1.0 处理；非正数消息拒绝或降级为 stopped。
4. 相同设备的旧 stateVersion、重复消息和延迟消息不得覆盖新状态。
5. 新 trackId 必须清理旧歌词请求和旧时间轴。
6. Android 在切歌、播放、暂停、Seek 时立即发送状态。
7. Android 持续播放时默认每 2 秒发送一次校准状态；这不是 UI 帧率，必须可测试。
8. Windows 收到 playing 时记录：

       basePosition = positionMs
       baseClock = monotonicNow()
       speed = playbackSpeed

   当前播放位置为：

       currentPosition = basePosition
                       + elapsed(monotonicNow, baseClock) * speed

9. paused/stopped 时冻结在最后一个有效位置。
10. 新状态、Seek、恢复播放和重连后的完整状态都要重新建立基准。
11. sentAt 只用于诊断或辅助排序，绝不能用于播放位置计算。

==================================================
七、歌词和时间轴规则
==================================================

LRC Parser 至少支持：

- [mm:ss.xx]、[mm:ss.xxx] 时间标签。
- 同一行多个时间标签。
- 无序输入排序。
- 空行和非法标签处理。
- 重复时间戳的确定性排序。
- 可选 offset 的解析或由 Windows 设置应用。

Timeline Engine 至少满足：

- 当前位置小于第一句时没有当前歌词行。
- 当前位置等于某句 startMs 时显示该句。
- 当前位置位于两句之间时显示最后一个 startMs <= position 的非空行。
- 超过最后一句时显示最后一句，直到歌曲停止或切歌。
- durationMs 已知时位置限制在 [0, durationMs]。
- 暂停后等待很久，当前行和位置都不继续前进。
- 恢复后从恢复状态重新推进。
- Seek 后立即跳到目标时间轴，不保留旧基准。
- 播放速度变化后使用新速度，不累计旧速度误差。
- 周期校准后不产生明显累计漂移；测试应证明长时间运行误差在项目设定阈值内。

歌词请求规则：

- 查询键使用 title + artist + album + duration 的标准化结果。
- 新歌曲到来后旧请求必须取消或结果被丢弃。
- 无同步歌词时不能把普通无时间轴歌词伪装成同步歌词。
- Provider 超时、无结果、服务错误和格式错误必须可区分并可观察。
- Provider 不可用时设备连接仍保持，任务栏显示明确的空状态或隐藏。

==================================================
八、Android 验收规则
==================================================

A-01：首次启动能解释 MediaSession 授权用途，并能进入系统授权页。

A-02：未授权时显示明确状态，不崩溃，不假装已读取歌曲。

A-03：授权后能读取至少一个真实播放器的 title、artist、album、duration、packageName、播放状态和位置。

A-04：播放器播放、暂停、恢复、Seek、上一首、下一首时，状态能在合理延迟内发生变化并发送。

A-05：多个活跃会话时选择规则确定、可解释，并优先当前 playing 会话。

A-06：播放器切换或没有活跃会话时不会继续发送上一首的陈旧状态。

A-07：Android 不申请和不使用 AudioPlaybackCapture、麦克风或音频录制能力。

A-08：持续播放时不是每几十毫秒发送消息；校准周期有测试或可观察证据。

A-09：局域网断开时不会无限创建连接/协程；重连使用退避并受生命周期约束。

A-10：配对密钥使用 Android Keystore 或等价的系统保护存储。

==================================================
九、Windows 验收规则
==================================================

W-01：首次启动能显示一次性 QR 配对信息，token 有有效期且不能重复使用。

W-02：错误 token、过期 token、未知设备和协议版本不匹配会被拒绝。

W-03：已配对 Android 在同一局域网出现后，Windows 可自动发现并连接，无需每次手动操作。

W-04：Windows 重启后，在开启开机启动和自动连接时能恢复连接；关闭设置时不应自行启动或连接。

W-05：Windows 断网后自动重连；恢复后使用 Android 最新完整状态重新校准。

W-06：歌词请求有取消、超时和旧结果隔离，不会因切歌显示上一首歌词。

W-07：任务栏只显示当前歌词，不创建桌面悬浮歌词或独立歌词窗口。

W-08：任务栏歌词不遮挡系统托盘、已有应用图标和正常任务栏操作，不抢输入焦点。

W-09：任务栏位于顶部、底部、左侧、右侧时都不会因为固定坐标而严重错位；无法安全布局时隐藏。

W-10：至少在 100%、125%、150%、200% DPI 下文字尺寸和可用宽度正确。

W-11：Windows 亮色和暗色任务栏下歌词均可读；用户关闭歌词时立即停止渲染但不必断开设备。

W-12：支持单行/双行、字体、字号、字重、颜色、对齐方式和时间偏移等必要设置；不做复杂主题系统。

W-13：任务栏 Shell/自动化接口异常时只影响渲染，不影响连接、歌词获取和同步核心。

W-14：Windows 设备密钥使用系统保护存储；日志不含密钥、完整 QR 或歌词全文。

==================================================
十、跨端端到端验收规则
==================================================

E2E-01：Windows 显示 QR，Android 扫码并授权后，双方完成一次配对。

E2E-02：配对后两端在同一局域网自动连接，用户无需重复输入地址或密钥。

E2E-03：Android 播放一首有同步歌词的歌曲后，Windows 自动获取该歌曲歌词并在任务栏显示当前行。

E2E-04：用户不操作 Windows、不在 Windows 播放声音时，歌词仍能出现和推进。

E2E-05：播放 → 暂停：任务栏歌词停止推进，不跳到未来行。

E2E-06：暂停 → 恢复：歌词从恢复位置继续，不重新从歌曲开头开始。

E2E-07：拖动 Seek：在一次状态更新或约定的短延迟内跳到目标歌词，旧基准不再影响结果。

E2E-08：上一首/下一首：旧歌词立即失效，新歌词加载完成前不能继续显示旧歌歌词。

E2E-09：切换 Android 播放器：Windows 最终显示新播放器当前歌曲，不依赖固定包名。

E2E-10：短暂断网后恢复：自动重连，重新校准，歌词不出现持续性累计漂移。

E2E-11：歌词 Provider 超时或无结果：连接不掉线，任务栏有明确空状态或安全隐藏。

E2E-12：连续播放至少 30 分钟后，时间轴误差满足项目设定阈值；阈值和实测结果必须记录。

E2E-13：至少三种首批重点播放器完成真实设备验证；不能只用模拟消息替代全部验收。

==================================================
十一、自动化测试最低要求
==================================================

必须先写测试再实现核心逻辑。最低测试集合：

1. Protocol
   - 合法 envelope 可以解析。
   - 缺失必填字段、错误版本、非法范围会被拒绝或明确降级。
   - 重复消息和旧 stateVersion 不覆盖新状态。
   - track.state 示例 JSON 始终能通过解析。

2. LRC Parser
   - 单时间标签、多时间标签、无序标签、非法标签、空行、重复时间戳、offset。

3. Timeline Engine
   - 起始位置、行间位置、恰好命中时间戳、歌曲末尾。
   - playing、paused、stopped、resume、Seek、speed change。
   - duration clamp、校准和长时间漂移。
   - 使用可控假时钟，不真实等待。

4. Request race
   - 旧歌曲 Provider 请求晚于新歌曲返回时，不得污染新歌曲。

5. Link
   - pairing success/failure、heartbeat、timeout、disconnect、backoff、reconnect。

6. Taskbar
   - 可用宽度、DPI、单行/双行和降级布局至少有无 UI 依赖的测试。

测试失败时不要标记完成。若测试无法在当前环境执行，明确写出缺失的 SDK、设备、系统版本或外部服务，并把 MVP 标记为未完成/受阻，而不是声称通过。

十三、完成条件
==================================================

只有同时满足以下条件，才能把目标标记为 complete：
```
